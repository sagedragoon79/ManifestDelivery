## 3. Camp multi-pickup — approach D — BUILT 2026-09-28 (uncommitted, Debug staged, NOT play-tested)

Implemented in `Patches/CampMultiPickupPatch.cs` (postfix on
`LogisticsTask.OnSearchSuccess`, `[HarmonyPriority(Priority.High)]`, once per task
via ConditionalWeakTable) behind `CampMultiPickup` (default off), with
`CampMultiPickupMaxStops` (3) and `CampMultiPickupDetour` (80u). Only touches
routes shaped [one producer pickup] → [one storage drop-off]; per item in the
pickup, adds stops at camp producers within the detour of the pickup (nearest
first), each ≥ 5% of capacity, capped by carry weight, destination free space and
the destination's max-quota room; inserts them before the original pickup in
nearest-neighbour order from the wagon. Also built: `MinLoadPercent` (default 20)
gating MD's ReturnTrip/CampHaul/HubHaul claims (camp supplies exempt); CampHaul
pools the same item at nearby producers toward the minimum when multi-pickup is on.
Known v1 limits: one item type per added stop (a producer with two items may get
two stops); extra stops don't register vanilla grab-while-pending.

**2026-09-29 play-test findings + fixes:**
- Tiny Camp restocks into workshops (5 Coal, 2 Planks) came from claims taking a
  building's INPUT requests along with the output the scan approved. Fixed:
  `ClaimRequester(..., include)` — each scan claims only the requests its own test
  approved (ReturnTrip `IsClaimable`, Camp `IsWorthwhileMoveOut`, Hub bulk+min-load).
  Remaining small Foundry coal runs are VANILLA wagon assignments (a Standard wagon
  did one too), not MD.
- Multi-pickup almost never found a partner: a producer activates its move-out only
  when its output storage is FULL (`Building.ShouldTransferProducedItemCount`:
  count >= capacity), and full producers are cleared at once. Fixed:
  `Tasks/CampProducers.cs` walks `resourceManager.allBuildingsRO` and reads
  LogisticsRequester's protected `moveOutItemRequests` (all requests, active or not)
  so extra stops (and Camp min-load pooling) include partly filled producers. Safe:
  pickups use MD's ItemReservation; `ReportItemsPickedUpForRequest` is empty, and
  `LogisticsDestinationSubTask` never checks `isActive` during the trip.

**Verdict:** augment the vanilla task. Let vanilla build the camp wagon's normal
one-producer TakeOut task, then in a postfix on `LogisticsTask.OnSearchSuccess`
insert extra pickup subtasks at other in-radius producers of the same item and add
matching drop-off actions at the same destination storage.

Refutation #1 ("dual-book desync") was wrong for TakeOut pickups — **✔ verified:**
- `ProcessRouteInternal` creates an `ItemRequestReservation` only for Deliver
  requests (L124786-124805). A TakeOut pickup holds only the source
  `ItemReservation` (`ReservationHelpers.ReserveExactAmountOfItem`, L124806); its
  drop-off holds only a `StorageSpaceReservation` (L124850, L124862-124866).
- A producer's move-out count is recomputed from its storage's UNRESERVED count
  (L330779-330786), so an extra `ItemReservation` automatically shrinks what other
  haulers see.
- Subtasks run strictly in list order (`GetNextSubTaskToStart`, L32494-32511); an
  invalid next subtask aborts the whole task.
- `LogisticsDestinationSubTask.AddLogisticsAction` registers the reservations and
  `CancelReservations` cancels them on abort (L121808-121856) — MD's added actions
  get vanilla's lifecycle.

Sketch (agent; APIs to verify at build time):
1. Postfix `[HarmonyPatch(typeof(LogisticsTask),"OnSearchSuccess")]` with
   `[HarmonyPriority(Priority.High)]` (before HaulDiagnostics). Guard per task
   (`ConditionalWeakTable`) — the same task can reach OnSearchSuccess twice.
2. Gate: `assignedReceiver is TransportWagon`, Camp mode. (Don't gate on
   `CampHaulRequester`; the subtask ctor postfix already cleared it.)
3. `subTasks` via `AccessTools.PropertyGetter(typeof(Task),"subTasks")`. Require one
   pickup subtask P0 (TakeOut action for a TakeOut request at a non-StorageBuilding
   inside WorkRadius) and one drop-off subtask D at storage S.
4. Budgets: remaining carry weight → `canCarry`; `space = S.GetAvailableStorageSpace`,
   capped by S's max quota.
5. Candidates (same scan as CampHaul): active move-out `SingleItemRequest` for the
   same item, owner not a StorageBuilding, `(req.storageExclusionFlags &
   S.storage.logisticsStorageFlags)==0`.
6. Per candidate: `n = min(unreserved, canCarry, space)`;
   `itemRes = ReservationHelpers.ReserveExactAmountOfItem(wagon, storB, item, n)`;
   `spaceRes = S.storageSpaceReservationManager.ReserveStorageSpace(wagon, S.storage, n)`
   (on null, cancel itemRes); `pick = new LogisticsDestinationSubTask(task, owner)`;
   `pick.AddLogisticsAction(new LogisticsDestinationAction(reqB, TakeOut, id, n, itemRes, null, null, storB))`;
   insert before P0 (so vanilla's grab-while-pending budget, L123471-123497, counts it);
   `D.AddLogisticsAction(new LogisticsDestinationAction(reqB, Deliver, id, n, null, null, spaceRes, S.storage))`.
7. v2: mixed items → second drop-off at a StorageBuilding from that item's CanStore
   bucket (`GetBaseScore(bucket) − distance`).
8. Optional: CampHaul waits until the camp's combined stock is worth a full load.
Unverified: pathing of inserted subtasks (only insert before the task starts).

Other options found: A′ custom storage-flag bits (bits ≥ `1<<8` are inert for
vanilla, L339203 etc.) to make a town-storage Deliver prefer camp producers — soft
filter, leaks when camp stock runs out; C camp depot + MD-owned bulk TakeOut (mines
precedent L347737-347775) — must self-exclude the depot as a destination; producers
DO appear in HasItem buckets (L330669-330678, base score 0 vs 60 for storages) but
quota requests exclude them by construction (L124244-124247) — likely why the old
"Deliver reframe" failed. The route job is `[BurstCompile]` (L122134): only
main-thread inputs can be changed.

## 4. Trading Post stocking by Hub wagons (feasible, MD-only)
- Stock work = `SingleItemRequest(itemID, traderStorage, Deliver, …, maxTripsPerQuery=1)`,
  no bulk min, created in `CheckWorkAvailabilityForTraderStockingItem` (L358907-358948);
  count = target − current at `RequestPriority.High` (L351024-351036). Only the post's
  workers are assigned, at `AssignmentPriority(-30, High)` (L358928-358934).
- Nothing restricts who may fulfill it; assignment is the gate (global set = fire water
  only, L60827). **✔ verified.**
- Wagons skip posts today because MD's `IsAlreadyAssigned(requester)`
  (`HubHaulSearchEntry.cs:208, 355-368`) is true — vanilla assigns every wagon to the
  post's quota TakeOut requests on the same requester (L354566).
- Design: Hub mode only, in `HubWorkRadius`, independent of multi-source. Pref
  `HubStockTradingPost` ("Hub Stocks Trading Post (experimental)", default false, KC
  "Camp & Hub", visible when HubHaulEnabled). In `FindBestHubRequester`: if
  `requester.owner is TradingPost tp`, find a stock request (`storageForAction ==
  tp.traderStorage`, unreserved ≥ ~25, not already assigned via
  `_wagon.logisticsAssignment.GetAssignedPriorityForRequest`, not
  `DeliverAlreadyCovered`) instead of the `IsAlreadyAssigned` check. Claim with the
  per-request `req.AssignWorker(_wagon, Default, Default)` (Default = (0, High),
  L121612 — don't use the trader's -30, it ranks below ParkWagon -10), set
  `HubHaulRequest`, `RegisterHubClaim`. Release on park (after fix #3) and in the
  `ItemBundleDroppedOff` postfix when `dropOffStorage == tp.traderStorage`
  (L360466). Exclude posts from ReturnTrip and the legacy whole-requester Hub path.
- Safe with the trader: shared request, job-level `searchReserved` (L122683-122690) and
  commit-time re-check (L124677-124687) prevent over-reservation. `traderStorage` has
  no space limit (L355501-355509). Buying/selling are instant UI transfers
  (L358731-358845). IEnterable is merchants-only. Add a minimum-load threshold.
